# Build Log 写作规范

## 唯一结构

文章固定为 **Hero + 8 个编号章节 + CTA + Footer**。不要再使用“6–8 章”或“9 段”等第二种口径。

| 区块 | 内容 |
|---|---|
| Hero | `Build Log · 00X`、H1、一句话摘要（规模 + 方法 + 结果）、日期、复刻对象、复刻页大小、Demo/算法入口、跳读目录 |
| 01 先读结论 | 三条以内，直接给结果（TL;DR） |
| 02 拿到真身 | iframe 地址、原始字节/行数、依赖情况 |
| 03 拆结构 | 模块图、重复单元、内容清单 |
| 04 设计与 Token | 颜色、字体、间距、动效参数 |
| 05 核心难点 | 数据解码 / 确定性 / 地图投影 / 动效降级，选一个讲透 |
| 06 工程修复 | 原页面 bug、移动端、可访问性 |
| 07 验收 | 视口表、功能表、控制台、打印 |
| 08 复盘 | 保留什么、放弃什么、下次做什么 |
| CTA | 打开复刻页、原始页面出处、免责声明 |
| Footer | 来源、版权、更新日期 |

## 写作要求

- 每个判断尽量带数字：`11,063 B`、`370 行`、`24/24`、`7.7s`、`2880×1800`。
- 代码只贴关键片段，不整文件搬运；片段要能说明一个决定。
- 对比用表格，趋势用图表，界面用截图；每张图都有说明。
- 原页面有缺陷时，写“修复前 / 修复后”，不要假装原作完美。
- 文章要能独立阅读，不依赖复刻页也能看懂方法与结论。
- 相对时间必须冻结为绝对日期，并注明快照时间。
- 涉及他人数据时先脱敏：金额、姓名、账号、精确位置、截图中的昵称与头像。

## 每篇至少包含

- 1 张首屏图或作品图。
- 1 张局部/对比图。
- 1 个参数表或验收表。
- 1 段关键代码。
- 1 个“修复前 / 修复后”的工程细节。
- 1 个明确的方法论结论。

## 图表规范

- 桌面/移动两套 SVG，媒体查询切换。
- 两套 SVG 的 `id` 必须区分（如 `decayTitleD` / `decayTitleM`），避免重复 ID。
- 每张图有 `<title>`、`<desc>`，图例用 HTML 文本，不把关键信息只放在颜色里。
- 移动图表限宽（例如 `max-width:440px`）并居中。
- 图表容器加 `role="img"` 与文字等价说明；纯装饰图形 `aria-hidden="true"`。

## 图片规范

- 截图转 WebP，宽度控制在 1000px 以内；首屏图可 `fetchpriority="high"`，下方图片 `loading="lazy"`。
- 手机截图用真实 375×812，不要用桌面截图硬裁。
- 图片内嵌会让文章变大；500 KB 左右可接受，但要确认首屏加载不拖沓。
- 所有 `<img>` 必须有 `alt`；装饰图用 `alt=""`，不要省略属性。

## 文章骨架

可直接复制 `assets/build-log-skeleton.html`，替换占位符。骨架包含 Hero、跳读、8 章、验收表、CTA 与免责声明占位，不包含具体案例数据。
