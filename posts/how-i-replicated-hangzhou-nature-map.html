Section 01

iframe 真身

01

从「领取礼物」到原始页面

顶层 URL ≠ 内容 URL

入口和前面几次一样：登录 WorkBuddy 成长中心，点击「领取礼物」，等弹窗里的 iframe 加载完，再从开发者工具里复制它的 src。真正的内容不在成长中心，而在一个可以直接访问的 COS 地址上。

case 04 / iframe src
# 原始页面（可直接访问）
https://acc-1258344699.cos.ap-guangzhou.myqcloud.com/
workbuddy/playbook/cases/hangzhou-3day-nature-map-guide/output.html

把页面保存下来之后，结构就很清楚了：一个 <script type="application/json" id="guide-data"> 装着全部行程，地图组件负责渲染。原始文件 183,032 字节、约 2,300 行，包含 3 个 group、12 个元素和 9 段 route_to_next。

原始页面的关键数据
对象数量 / 值用途

地图占位符YOUR_KEY · __WB_HTTP_PORT__ · __WB_TMAP_SECRET__独立打开时无法补全

问题也在这里：腾讯地图脚本需要有效的 key 与 secret。原页面在 WorkBuddy 的宿主环境里能拿到这些值，单独保存成静态文件后，它们仍然只是占位符。底图不会加载，地图区域是黑的。这就是这次复刻真正的起点。

先保存，再动手

不要对着 iframe 截图猜结构。把原始 HTML 保存到本地，确认 guide-data 能解析、路线字段完整，再决定哪些保留、哪些替换。后面所有坐标和文案都来自这份数据。

Section 02

轨迹解码

02

把 9 段轨迹从字符串里解出来

首点是纬度，后面是增量

原始轨迹不是 GeoJSON，而是一串用逗号分隔的数字。第一版按常规的「纬度、经度」顺序去解，结果每条线都飞到了城市的另一头。把终点和 route_ext.endPoint 一对比，规律很快显现：

route / decode
// 首点：纬度、经度
let lat = nums[0], lng = nums[1];

// 之后每一对：经度增量、纬度增量，单位 1e-6 度
for (let i = 2; i < nums.length; i += 2) {
  lng += nums[i] / 1e6;
  lat += nums[i + 1] / 1e6;
  points.push([lat, lng]);
}

判断依据不是「看起来像」，而是终点误差。以白堤这一段为例：按「纬度增量、经度增量」解，终点会偏出 2.4 km；把增量顺序换成「经度、纬度」，误差降到 约 90 m。放大到 105 或 103 更不可能，点会直接飞出杭州。

白堤段终点与 route_ext 的偏差
解码方式终点偏差结论
1e6 · 纬度增量在前约 2.4 km方向反了，弃用
1e6 · 经度增量在前约 90 m采用
1e5 / 1e3 缩放飞出杭州量级不成立

解出来的 9 段轨迹合计 54,855 米。分摊到三天，Day1 只有 2.2 km，Day2 约 24.0 km，Day3 约 28.7 km——这也解释了为什么 Day2、Day3 的线会跨过半个城区。

2,154 mDay1 · 西湖环线
24,023 mDay2 · 龙井与九溪
28,678 mDay3 · 西溪与东站
54,855 m合计 · 页面显示 55 km

还有一个必须承认的细节：轨迹终点和站点坐标并不总是重合。短途的断桥段只有 2 个点，路线起点离断桥约 100 m，终点离白堤约 550 m；其余段落也常见几十米到 1.5 km 的偏差。我没有把线硬拽到站点上，而是在 gap 超过 2.5 个地图像素时补一段虚线接驳，让「真实轨迹」和「站点位置」各自保持诚实。

route / connector
// 只在明显断开时补虚线，不修改原始轨迹
if (distance(station, routeStart) > 2.5) {
  svg.append('path')
     .attr('class', 'leg-conn')
     .attr('d', `M${station.x} ${station.y}L${routeStart.x} ${routeStart.y}`);
}

Section 03

底图方案

03

底图不能等到运行时再想办法

77 张瓦片 → 1 张 WebP

腾讯地图这条路走不通后，我认真比较了三种方案。最后选的不是「最像原版」的，而是「最不依赖环境」的。

底图方案对比
方案代价结论
申请腾讯地图 key需要账号、域名白名单与 secret；静态 demo 无法安全携带不可行
Leaflet + 在线瓦片运行时依赖网络与第三方服务；限流、离线、隐私都不可控放弃
构建时预渲染并内嵌文件变大；底图是静态的，不能无限缩放采用

底图范围按内容包围盒反推：z14 的 x 13654..13664、y 6743..6749，正好 77 张 256px 瓦片，拼成 2816×1792。纬度约 30.1831–30.3160，经度约 120.0146–120.2563，覆盖西湖、龙井、西溪和杭州东站。

basemap / build time
# 只跑一次：抓取、拼接、调色、压缩
for y in range(6743, 6750):
  for x in range(13654, 13665):
    fetch(f"https://tile.openstreetmap.de/14/{x}/{y}.png")

stitch(2816, 1792)  # 11 × 7 张
tone(0.40, 1.055, 0.92)  # 饱和度 / 亮度 / 对比度
resize(1920, 1222).save("basemap.webp", quality=66)

77 张原图拼起来是 2.2 MB，直接转 JPEG 约 1.4 MB；调色后缩到 1920×1222、WebP q66，最终只有 383,770 字节，base64 后约 512 KB。这个尺寸足够撑住 1440px 屏，又不至于让页面变成几兆。

阶段尺寸 / 格式体积

拼接原图2816×1792 JPEG q80约 1.4 MB

为什么停在 z14？z15 的瓦片数会从 77 张变成约 300 张，像素量翻四倍，页面也会跟着膨胀。对一张以「看清三日路线」为目标的地图来说，z14 的街道、湖岸和绿地已经够用；再放大时，浏览器会做插值，清晰度会下降，但信息层级仍然成立。

取舍

静态底图换来了「打开即见、零地图请求」，代价是不能像在线地图那样无限缩放。页面给缩放设了上限，并在缩放到边界时保持地图覆盖可视区域，避免露出空白。

Section 04

投影与站点

04

把 12 个站放回同一张地图

Web Mercator，不是等距拉伸

底图是 Web Mercator 瓦片，站点和轨迹也必须用同一套投影，否则越往南北两端偏得越多。页面里保留了与构建脚本一致的公式：

map / web mercator
const Z = 14, X0 = 13654, Y0 = 6743;
const X1 = 13665, Y1 = 6750;

function mercY(lat) {
  return (1 - Math.log(Math.tan(lat * Math.PI / 180)
    + 1 / Math.cos(lat * Math.PI / 180)) / Math.PI) / 2
    * Math.pow(2, Z);
}

function project(lat, lng) {
  const mx = (lng + 180) / 360 * Math.pow(2, Z);
  return {
    x: (mx - X0) / (X1 - X0) * 1920,
    y: (mercY(lat) - Y0) / (Y1 - Y0) * 1222
  };
}

12 个站点投影后落在一个 1276 × 963 的内容包围盒里。页面没有把地图铺满就完事，而是把这个包围盒放进「面板右侧的安全区」：桌面端左边让出 326px 面板，移动端把底部抽屉以上的区域当作可视区。站点不会躲到面板下面，也不会被顶部站点条压住。

站点一多，标签就会打架。断桥、白堤、湖滨晴雨、知味观这四站在地图上挤成一团，缩到全览时最多只能容下一两个标签。页面没有硬把所有名字都塞进去，而是先测量标签矩形，再依次检查三种冲突：

越界标签超出安全区就隐藏
标签互压已放置的矩形参与碰撞
压到图钉其他站点的圆点也要避让

markers / label collision
// 关键：class 加在 marker 上，CSS 才能命中 .pin-label
if (outsideSafe(r) || hitsLabel(r, placed) || hitsPin(r, pins)) {
  el.classList.add('label-off');
} else {
  placed.push(r);
}

这里踩过一个很隐蔽的坑：第一版把 label-off 加到了 .pin-label 本身，而 CSS 选择器写的是 .marker.label-off .pin-label。结果 class 加了，样式没生效，标签在过渡结束后仍然留在屏幕上。把 class 改挂到 .marker 上，一切才对上。

Section 05

移动端

05

移动端不是把桌面版缩小

重算地图区域与弹窗边界

桌面端的左面板可以一直占着 326px；在 375px 宽的手机上，这块面板会让地图只剩一条缝。复刻页在 820px 以下切换成底部抽屉，最高占 48% 屏高，地图仍然保留完整的横向视野。

layout / safe area
const safe = mobile
  ? { left: 14, right: vw - 14, top: 88, bottom: p.top - 10 }
  : { left: p.right + 18, right: vw - 18, top: 86, bottom: vh - 18 };

// 基准缩放：内容 fit 与「至少覆盖 82% 视口」取较大值
const scale = Math.max(fit, cover * 0.82);

移动端最开始的问题是西侧的西溪湿地被裁掉。原因不是布局，而是基准缩放只按内容包围盒算 fit，地图宽度小于可视区，clampView 又把画布推到了左边。改成 Math.max(fit, cover * 0.82)，再给内容加 20 个地图像素的 padding，西溪和杭州东站才同时留在画面里。

移动端问题与修复
问题根因修复
西侧站点被裁只按内容 fit，地图宽度不足cover * 0.82 + 20px padding
顶部站点被站条遮挡安全区顶部只留了 18px桌面 86px / 移动 88px
标签压住其他图钉只检查标签互压把 pin 矩形也加入碰撞
弹窗上下都放不下只做 above / below 两种定位detached 居中 + 隐藏箭头
弹窗被缩放控件压住popup 的 z-index 低于控件提到 --ui + 20，移动端打开弹窗时隐藏控件
终点站仍显示「查看下一站」display:inline-flex 覆盖了 [hidden]补 .nx-go[hidden]{display:none}

弹窗是最容易在边缘翻车的地方。桌面端它通常出现在站点上方，靠近顶部时翻到下方；移动端地图区域只有三百多像素高，上下都放不下时，就切成 detached 模式：在安全区里居中，隐藏小箭头，不再假装自己指向某个点。箭头的位置也单独算了一个 --arrow-x，避免弹窗被左右边界夹住时，箭头还固执地指向空白。

缩放控件的层级已修复

桌面端控件和弹窗都可能出现在右下角。popup 最初用了 --ui - 20，结果被按钮盖住；现在弹窗在控件之上，移动端则在 body.popup-open 时直接淡出控件。

隐藏属性也会输已修复

popupNextGo.hidden = true 在 DOM 上是对的，但 .nx-go{display:inline-flex} 的优先级更高，按钮仍然显示。补一条 [hidden] 规则，才真正消失。

手势方面，桌面用滚轮和拖拽，移动端用 Pointer Events 同时处理单指拖动和双指缩放。所有视图变更都会经过 clampView，确保地图不会在拖到边界后露出底色；重置按钮则回到「三日全览」，顺便清掉日期筛选和当前弹窗。

Section 07

复盘

07

复盘：地图是数据的另一种排版

4 条可复用经验

这次之后，我对「复刻」的理解又多了一层：地图不是一张背景图，而是把经纬度、投影、边界、标签和交互重新排成一张可读的版面。任何一层偷懒，都会在某个视口里露出来。

01
先保存原始数据

iframe 只是入口。把 HTML 和 JSON 保存下来，逐条核对 3 个日程、12 个站点、9 段路线，再开始画界面。

guide-data 是唯一事实源
02
坐标系是硬约束

Web Mercator、瓦片范围、内容包围盒必须使用同一套参数。投影错了，线会飞；边界错了，站会躲到面板后面。

同一套 X0 / Y0 / Z
03
移动端要重新排版

底部抽屉、安全区、detached 弹窗，都不是桌面样式的等比缩小。375px 宽时，地图的可用高度只有三百多像素。

3 档视口 + 真实手势
04
边界状态才是体验

最后一个站点的按钮、靠近边缘的箭头、被夹住的标签、拖到尽头的地图——这些状态决定页面是否可信。
