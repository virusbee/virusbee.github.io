02 / The field
Perlin 噪声
02

5000 颗粒子，如何找到下一步

noise → angle → velocity

每一帧，粒子只做一件事：用当前位置去问噪声场「我该往哪走」，然后朝那个方向迈出 1–3 像素。问一次，走一步；5000 颗粒子问 5000 次，画面就向前长了一帧。

Particle.update · 核心四行
const angle = noise.noise2D(
  this.x * 0.003,
  this.y * 0.003 + frameCount * 0.0003
) * Math.PI * 4;

this.x += Math.cos(angle) * this.speed;
this.y += Math.sin(angle) * this.speed;

Perlin 噪声和「每颗粒子随机一个角度」的区别在于连续性：相邻坐标的噪声值彼此相关，所以邻居会朝相近的方向走，轨迹自然汇成带；纯随机只会得到一团没有方向的噪点。原作还把噪声按 frameCount * 0.0003 缓慢推移，整片流场会在大约 56 秒里漂移一个噪声单位。

原作里真正控制画面的七个常量
常量值作用
PARTICLE_COUNT5,000每帧 5,000 次更新与描边
NOISE_SCALE0.003约 333px 一个噪声单元，流线尺度很大
SPEED2 × (0.5–1.5)每帧 1–3px，60fps 下约 60–180px/s
LIFE400–900 帧6.7–15 秒后重生，避免轨迹无限变长
角度倍率π × 4把噪声映射到更宽的方向范围
时间项0.0003 / 帧流场缓慢漂移，画面不会完全静止
淡出0.0015 / 帧决定轨迹能活多久，下一节展开
为什么是 π × 4

Perlin 噪声返回大约 −1 到 1。乘 π × 2 已经能覆盖一整圈方向；原作乘了 π × 4，相当于让方向变化更敏感，细小的噪声差异会被放大成更丰富的弯折。由于 cos/sin 本身有周期性，超过一圈也不会出错。

03 / The exposure
0.0015 淡出
03

每帧只擦掉 0.15%，于是运动变成了长曝光

time = alpha

整件作品最关键的并不是噪声，而是下面这两行。它没有清空画布，而是每帧盖上一层透明度 0.0015 的黑：

animate · 先淡出，再画新一帧
ctx.fillStyle = 'rgba(10, 10, 10, 0.0015)';
ctx.fillRect(0, 0, width, height);

for (const p of particles) {
  p.update();
  p.draw();
}
w(n) = (1 − 0.0015)n
n 为帧数；60fps 下，半衰期约 7.7 秒。
30 秒后剩 6.7%

这层黑不是「背景色」，而是时间。一条线画下去之后，每过一帧就只剩 99.85% 的亮度；旧轨迹不会突然消失，而是慢慢退到黑色里。5000 颗粒子每秒留下约 30 万段短笔画，叠在一起就成了像长曝光照片一样的丝绸纹理。

每帧淡出 0.0015 0.005 0.02
剩余亮度随时间的变化。0.0015 的曲线在 30 秒时仍有约 6.7%，0.02 的曲线不到 1 秒就接近黑色。
同一套粒子，只改淡出值，轨迹的「寿命」就会完全不同
每帧淡出半衰期观感
0.00157.7 s原作；长曝光、丝绸、缓慢堆积
0.0052.3 s中长轨迹，细节更清楚
0.011.15 s短轨迹，更像实时笔刷
0.020.57 s接近瞬时拖尾
0.050.23 s几乎只看到粒子本身
噪声决定「往哪走」，淡出决定「走多远」。真正让这张画有气质的，是后者。

复刻页保留了这个 0.0015。给文章生成封面时，我先同步跑了 280 帧，此时一条旧线还保留约 66% 的亮度，足够让画面看起来像已经呼吸了几分钟。

04 / The seed
可复现性
04

显示 Seed，不等于能复现同一幅画

random ≠ reproducible

这是我在这件作品里踩到的最有意思的坑：原作把 Seed 显示在右上角，看起来像一个可复现的编号；但把同一个 Seed 重新加载，画面并不会回来。

原因在随机数的分配。Seed 只被传进了 PerlinNoise，用来打乱那张 256 项的置换表；而粒子的初始位置、速度、寿命和颜色，仍然全部来自 Math.random()。换句话说，Seed 固定的是河道，没有固定水里的船。

原作的随机数分布
// 只固定了流场
noise = new PerlinNoise(seed);

// 粒子仍然是真随机
this.x = Math.random() * width;
this.y = Math.random() * height;
this.speed = SPEED * (0.5 + Math.random());
this.colorIndex = Math.floor(Math.random() * palette.length);

我的第一版复刻也只做了「URL 里带 seed」。把链接发给别人，对方看到的种子号一样，画面却完全不同。要让它成为真正的可复现作品，必须把所有随机来源都接到同一个种子下。

复刻页 · 粒子随机流也用种子初始化
function mulberry32(a) {
  return function() {
    a |= 0;
    a = (a + 0x6D2B79F5) | 0;
    let t = Math.imul(a ^ (a >>> 15), 1 | a);
    t = (t + Math.imul(t ^ (t >>> 7), 61 | t)) ^ t;
    return ((t ^ (t >>> 14)) >>> 0) / 4294967296;
  };
}

particleRng = mulberry32((seed ^ 0x9E3779B9) >>> 0);

复刻页把噪声置换和粒子随机拆成两条独立的流：一条由原作的 LCG 生成，一条由 mulberry32 生成，二者都从同一个 Seed 派生。这样 Seed 才能同时决定河道和船。

验证

在同一个 656×761 视口里，用 reset(90370) + 40 帧渲染两次，导出的 PNG data URL 完全一致；换成 90371 后立刻不同。Seed 链接复制的不再只是一个数字，而是一组确定的初始条件。

同一套参数、同一个视口，只换 Seed，流场的拓扑就完全不同。复刻页右上角的 Seed 可以直接点击复制带参数的链接；在同一设备和视口打开，会从同一组初始条件重新生长。

需要说清楚边界：Seed 固定的是初始条件与流场，不是某一帧的录像。不同刷新率、不同视口、不同打开时长，都会让画面停在不同阶段；但同一条件下重新开始，作品会沿着同一条轨迹长回去。

05 / The edges
真实页面
05

让画布在真实页面里活下来

resize · DPR · pause

把原作放进真实浏览器后，问题很快出现。它们不影响「第一眼像不像」，却决定了这件作品能不能被认真使用。

Resize 会换掉整幅画原作

window.addEventListener('resize', ...) 里直接调用了 regenerate()。移动端地址栏收起、开发者工具打开、甚至截图工具改变视口，都会触发一次全新 Seed。我在两次读取之间看到 Seed 从 46957 变成 97529，才意识到不是随机数在跑，而是 resize 在重置。

快照 + 坐标缩放复刻

先保存旧 canvas 快照，调整尺寸后把它拉伸回新画布，再按宽高比例缩放每颗粒子的 x/y/prevX/prevY。Seed、帧数和轨迹都保留；代价是极端长宽比下画面会被拉伸。

Retina 上发虚原作

canvas 的像素尺寸直接等于 innerWidth/innerHeight，在 2× 屏幕上等于用一半分辨率画画，细线会糊。

DPR 上限 2×复刻

物理像素 = CSS 尺寸 × min(devicePixelRatio, 2)，再用 setTransform 把绘制坐标留在 CSS 像素。1440×900 在 2× 屏上是 2880×1800，实测仍能跑 60fps，导出的 PNG 也更大。

没有暂停原作

只有 Regenerate 和 Save。想仔细看一帧、或者让风扇安静下来，只能关掉页面。切到后台再回来，FPS 采样还会被一个巨大的时间差污染。

暂停 / 恢复 / 隐藏即停复刻

新增 Pause；暂停时 FPS 显示「—」。页面隐藏时取消 RAF，回来时重置 lastTime；小于 4ms 或大于 250ms 的帧间隔直接丢弃，不进入 FPS 平均。

resize 前的快照，是保留作品的关键一步
const snap = document.createElement('canvas');
snap.width = canvas.width;
snap.height = canvas.height;
snap.getContext('2d').drawImage(canvas, 0, 0);

// 改变 canvas 尺寸、重设 DPR 变换
// 再把快照画回新尺寸，并缩放粒子坐标
ctx.drawImage(snap, 0, 0, width, height);

保存按钮保留了原作的同步 toDataURL('image/png') 路径：移动端 Safari 对异步回调里触发的下载更挑剔，同步路径更稳。代价是导出瞬间会产生一段较大的 base64 字符串；在 656×761、2× 的测试视口里，PNG 尺寸是 1312×1522，约 4.8MB。

取舍

我选择让 resize 保留画面，而不是像原作那样重新生成。前者牺牲了一点几何纯度，后者会让用户在地址栏收起的瞬间丢掉整幅画。对一件「慢慢长出来」的作品，保留比纯净更重要。

06 / Small screens
375px 重排
06

365×209 的弹窗，和 375×812 的页面

one canvas, three layouts

原作的所有 UI 都固定在四角：标题左上，参数面板右上，按钮底部居中，边距 24px。放进 364.5px 宽的礼物弹窗后，标题和 180px 宽的面板几乎贴在一起；到了 375px 的手机上，三个按钮也需要重新排。

复刻页的窄屏策略

  • ≤ 560px：参数面板变成标题下方的三列横条，Seed / Particles / FPS 一字排开。
  • ≤ 860px：站点入口移动到按钮上方居中，避免和底部控制条抢位置。
  • ≤ 380px：进一步缩小按钮字号和内边距，三个按钮仍然同排。
  • ≤ 460px 高：参数面板压缩，并把标题副行隐藏；横屏时不和标题重叠。
  • 安全区：底部按钮和入口都加上 env(safe-area-inset-bottom)，适配刘海屏手势条。

测试值：375×812 下 scrollWidth = 375，标题底部 56px、参数条顶部 70px；按钮高 44px，入口在按钮上方 12px 处，没有重叠。

参数面板的窄屏重排
@media(max-width:560px) {
  .info-panel {
    top: 70px; left: 16px; right: 16px;
    display: grid;
    grid-template-columns: repeat(3, 1fr);
  }
  .controls {
    left: 12px; right: 12px; bottom: calc(14px + env(safe-area-inset-bottom));
    transform: none;
  }
  .btn { flex: 1; min-height: 44px; }
}

这里没有把参数或按钮藏起来。小屏不是「删功能」的同义词，而是把同一组信息换一种排法：纵向的面板变横向，居中的按钮组变等宽，站点入口从底部左侧移到按钮上方。画面仍然占满全屏，控件只在需要时压住边缘。

短屏补充

在 320×450 这类又窄又矮的视口里，单靠「宽度 ≤ 560」会让面板和标题在同一行抢空间。复刻页额外加了 (max-width: 560px) and (max-height: 460px) 的组合查询：面板保持在标题下方横排，标题副行隐藏，按钮贴底。

结论

它不只是「看起来像原作」。它能在同一组条件下重新长成同一幅画，能在暂停时保持一帧，能在手机上不挤在一起，也能让选择减少动态效果的人先看到一张完整的静帧。

08 / Review
370 行之后
08

370 行之后

what remains

这是五期里原作最短的一次，却也是最需要克制的一次。代码本身几乎没有可拆的架构：一个噪声类、一个粒子类、一个动画循环。难点不在「写出来」，而在「不把它写坏」。

我加的东西，基本都指向同一个问题：让这件作品可被认真使用。Pause 是为了看清一帧；Seed 链接是为了把同一幅画交给别人；resize 保留画面是为了不让地址栏的收起毁掉几分钟的生长；减弱动效是为了让「不动」也成为一件完整的作品。

最喜欢的发现还是那个 0.0015。它小到在代码里几乎看不见，却决定了整件作品的时间感。噪声场给出方向，粒子给出密度，颜色给出情绪，而淡出给出记忆。没有它，这只是一张实时更新的线框；有了它，5000 颗粒子才像在黑色里留下了一段曝光。

显示一个参数，是一种承诺。要么让它真的可复现，要么就别把它叫作 Seed。

下一步如果继续玩，我可能会加一个色板编辑器，或者把 8 秒的生长过程录成 WebM。但那是另一件作品了。这一次，先把 370 行里已经存在的诗意保留下来。
